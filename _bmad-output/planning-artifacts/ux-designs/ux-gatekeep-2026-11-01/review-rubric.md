# Spine Pair Review — gatekeep

## Overall verdict

Not yet safe to hand to architecture or story-dev. The visual extraction, screen inventory and document shape are good, and nothing here needs a redesign. The behavioural contract fails at the places that matter most for an identity product: the password-step recovery path can bypass FR-27, first-Factor enrolment doesn't meet FR-25's stolen-password rule, and the Design Delta misses deferred controls that would ship by default on Admin pages marked v1.

One update pass that resolves the sign-in branches, the Editor/Owner split, the Design Delta and the missing Deployment-level surfaces should clear every critical and high finding. Three items need the owner's ruling rather than an edit: how FR-25's "stolen password" rule is met, whether Hosted Login has a dark theme, and whether Liquid survives in email templates.

## 1. Flow coverage — adequate

Checked: six UJs, §7.3 required screens and every FR with a user-visible path. All UJs have a flow or an explicit Operator note. Flows 1–9 and R1–R3 have protagonists, numbered steps and climaxes. Sign-in-order diagram checked against FR-25, FR-27, FR-29 and FR-47.

### Findings

- **[high]** FR-50 has no flow and is under-specified, though §7.3 lists "FR-50 actions" as screens to design and UJ-3/UJ-6 depend on them. The Incident response row says "Two actions" and doesn't name them. FR-50 needs four: Tenant revoke-all; Tenant forced password reset plus TOTP re-enrolment; Tenant security notice to all Users; Deployment Owner cross-Tenant action including revoking all Signing Keys. The Deployment-wide action has no location: the sidebar item is Tenant-scoped and the avatar menu holds only Tenants, Admins and Deployment Log (EXPERIENCE L54, L61, L248, L500). *Fix:* add a flow for Incident response, list each action with role, scope, confirmation copy and progress or partial-failure state, and give the Deployment-wide action a home.
- **[medium]** The "sign-in order" diagram says the server enforces "this order for every sign-in" but omits the breached-password branch, blocked and locked states, Recovery Code paths, Passkey creation and Recovery Code display. It also sends Email verification required straight to the second-factor check, while L161 sends the other-browser case back to "Sign in to continue" and the same-browser case to Passkey creation (EXPERIENCE L370–388). FR-47's transaction states will be derived from this diagram. *Fix:* extend it to all v1 branches, or relabel it "happy path only" and add the full state list.
- **[medium]** Several v1 paths have state rows but no flow: social sign-in (FR-20), Account Portal sensitive change (FR-35), Admin invite to credential setup (FR-39, FR-46), bootstrap (FR-2) and email recovery (FR-27). Social and bootstrap are the riskiest because the rows don't show the sequence (EXPERIENCE Key Flows). *Fix:* add short flows for at least social sign-in, bootstrap and a Portal sensitive change.
- **[medium]** Flow 10 (UJ-5) has no failure path, though failures clearly apply: unauthorized Permission requested, Permission removed before refresh (FR-16), and the Application lacking Client Credentials (FR-13) (EXPERIENCE L491–496). *Fix:* add a Failures line.
- **[low]** Flow 3 step 1 has Tomás choosing a code "on Login", but the Design Delta puts "Email me a code" on the password step, and a choice on the identifier step would need different wiring (EXPERIENCE L346, L420). *Fix:* change step 1 to match the Delta.
- **[low]** Flow 2's failure path promises "Generic error and a resend path", but the Generic error row offers only "Back to the Application" (EXPERIENCE L187, L414). *Fix:* add a resend action for verification links, or remove the promise.

## 2. Token completeness — adequate

Checked: all 24 Design System colours have light and dark values, and the frontmatter hexes I recomputed match the stated ratios. Extension tokens, focus treatment and component-state pairs were recomputed from hex.

### Findings

- **[high]** Focus is only defined for inputs. `input-focus` and `hosted-input-focus` exist, but buttons, links, tabs, rows, toggles, checkboxes, method rows and the code input have no focus token. The ring can't serve alone: `ac-sf` on `sf` is 1.15:1 light and 1.19:1 dark, so on inputs the `ac` border does all the work, and that border is invisible on a primary button. design-consistency A-1 says "Applies to all controls", and the exports draw none of this (DESIGN L207–209, L315–317; EXPERIENCE L314). NFR-16 needs this on Hosted Login. *Fix:* add one `focus-ring` token with an `ac` outline and offset, verified at 3:1 against adjacent colours, and state that it applies to every interactive element. This fills a gap and doesn't change a resting visual.
- **[medium]** The Contrast table omits pairs that fail its own targets. `ac` check on the toast is 1.93:1 in dark. The knob on an on toggle is 2.26:1 in dark. The off toggle track on `sf` is 1.56:1 light and 1.49:1 dark. `tx3` table heads on `sf2` are 3.24:1 and 3.46:1, while L358 limits `tx3` to meta and placeholder. `code-gutter` is 2.45:1 and 2.69:1. These are Admin-only, so nothing in the PRD blocks them, but the table reads as complete (DESIGN L217, L247, L369–380). *Fix:* add these rows with a "known exception, Admin only" status, plus the passing Hosted pairs consumers need: `bad` on `sf` 5.61, `ac-tx` on `sf` 6.94, `tx2` on `bg` 6.83.
- **[medium]** Hosted Login's theme mode is undecided. The Hosted export has no dark theme (0 `data-theme` or `prefers-color-scheme` rules), yet L354 says every token has a dark value, and Foundation grants light and dark only to the Admin Dashboard. The Tenant theme contract covers one primary colour with no dark derivation (DESIGN L354, L458–463; EXPERIENCE L20–21). *Fix:* state "Hosted Login is light-only in v1", or define the dark behaviour and theme derivation. Owner ruling.
- **[medium]** `shadow: sh` is a dangling value, and `sh`, `scrim` and `gkIn` have no frontmatter tokens, although design-consistency A-10 and A-15 say `scrim` and `motion` values were added. Prose holds the only values (DESIGN L274, L412–415). *Fix:* add a documented extension block for shadow, scrim and motion, or correct the audit's claims.
- **[medium]** Tenant derived colours are undefined. "Derived `ac-sf`, `ac-tx`, `on-ac`" has no algorithm, and the 4.5:1 refusal rule doesn't list which pairs are tested, nor a 3:1 check for `ac` as focus edge on `sf`. FR-34 says "colours", while DESIGN narrows this to one primary colour without tagging the decision (DESIGN L456, L461). *Fix:* commit the derivation or make it an explicit architecture question, list the tested pairs, and tag the single-colour narrowing `[ASSUMPTION]`.
- **[medium]** `checkbox` defines only the checked state, and no radio token exists. The unchecked state is the initial state on Recovery Code display and terms, and its edge needs 3:1 on Hosted Login (DESIGN L219–223, L430). *Fix:* add `unchecked-border: {colors.tx3}` and a radio token.
- **[low]** "Every token has a light and a dark value" is false for `knob` and the four `code-*` extensions. They appear to be theme-invariant, so this is low rather than the rubric's default critical, but the frontmatter doesn't say so (DESIGN L60–65, L354). *Fix:* add a line declaring them theme-invariant.
- **[low]** `ring: 3px '{colors.ac-sf}'`, `border: 1px dashed '{colors.bd2}'` and `typography: 500 13px Geist` aren't pure references, so a flattening resolver won't handle them. The script's "refs resolve" result doesn't cover this (DESIGN L175, L209, L267, L326). *Fix:* split into separate width, style and colour fields, and add a button typography token.
- **[low]** `sf3` is described as the hover colour, but `table.row-hover` and the Admin export's ghost hover use `sf2`. Button hover has no token at all (DESIGN L251, L356). *Fix:* correct the prose and record hover for each button variant.
- **[low]** Extension typography tokens have no `lineHeight`, and `label` has none either (DESIGN L95–99, L106–134). *Fix:* add the values.

## 3. Component coverage — thin

Checked: every named component across frontmatter, DESIGN Components, EXPERIENCE Component Patterns and state tables. The named rows that exist are real rules. The gaps are components with only one half, or neither.

### Findings

- **[high]** Components that load-bearing state rules depend on have no visual spec: skeleton rows and button spinner (the global loading states), the dropdown menu (Tenant switcher, avatar menu, User · Actions), select (DS draws it, DESIGN omits it), multi-line URL field, and Password field Show. The exports have 0 skeleton and 0 spinner, so a builder has nothing to extract (DESIGN L427–439; EXPERIENCE L90, L112, L125, L286). *Fix:* add anatomy to DESIGN built from existing tokens. This extends the system and doesn't redraw it.
- **[medium]** `code-input` conflicts with Recovery Code entry. DESIGN says it's "one field for every code screen", but EXPERIENCE fixes `inputmode="numeric"`, `autocomplete="one-time-code"` and submit-when-complete. Recovery Codes are `XXXX-XXXX`, so numeric keyboards and OTP autofill are wrong for them (DESIGN L447; EXPERIENCE L110, L152, L277). *Fix:* add a recovery variant with a text inputmode and no OTP autocomplete, or use `hosted-input` with mono type.
- **[medium]** Hosted Login has no error input, secondary button, social button or Account Portal treatment in frontmatter. `input-error` is Admin-only, and the portal uses `toast`, `banner`, `modal` and skeleton with no Hosted sizing (DESIGN L303–317, L445; EXPERIENCE L193–196). *Fix:* add `hosted-input-error`, `hosted-button-secondary`, `social-button`, and a rule for which Admin components the portal reuses and at what scale.
- **[medium]** Behaviour rows are missing for `button-secondary`, `button-ghost`, `checkbox`, `empty-state`, `badge-status`, `recovery-code-block`, `status-icon`, `json-viewer`, `hosted-button-primary`, `hosted-input`, social buttons and `top-bar`. Most are trivial, but `recovery-code-block` (Copy, Download, filename, whether Back is safe) and social buttons (loading, return from provider) carry real rules (EXPERIENCE L88–115). *Fix:* add rows for those two, and a single line saying the rest follow generic control behaviour.
- **[medium]** Visual specs are missing for the blocks that Admin v1 pages are built from: stats, cards, bars, settings rows and the RBAC matrix. All are in the v1 map as Section blocks and appear on Health, Quickstarts, Passkeys and RBAC. Visual anatomy is also missing for Typed confirmation, One-time reveal and Copy control (DESIGN Components; EXPERIENCE L612). *Fix:* add one line each with tokens.
- **[medium]** The strength meter's rule checklist keeps the export's "✓ Not found in known breaches" (Hosted L80–94), but EXPERIENCE L111 says the breach check runs on the server at submit only. The checklist can't show that state as typed, and the Delta doesn't mention it (DESIGN L450). *Fix:* add the removal to the Design Delta, or show the rule as unverified until submit.
- **[medium]** Social buttons at 42px contradict the "at least 44px on controls" floor. Separately, the 15px `checkbox` is below 24px unless its label is the target, which isn't stated (DESIGN L222, L445; EXPERIENCE L321). *Fix:* raise social buttons to `control-h-hosted`, or lower the floor to WCAG's 24px with a note, and state that the checkbox label is part of the target.

## 4. State coverage — thin

Checked: every IA surface and §7.2 screen against empty, cold load, focus, error, offline and permission-denied. Global table plus per-screen tables cover far more than the exports do, and Viewer, offline and session-expiry handling exist. The weak points are Editor permissions, whole missing surfaces and Hosted Login edge branches.

### Findings

- **[high]** Permission-denied covers Viewers only. FR-39 has an Editor/Owner split on client secrets, password policy, MFA policy, Connection credentials, email provider, Tenant label, Signing Keys, Management API access, export or erasure, and FR-50. The global banner "You have view-only access to this Tenant" is false for an Editor, and only two rows mention Owner. Direct examples: Create Application by an Editor reaches a one-time secret reveal, although FR-39 reserves secrets for Owners (FR-11 vs FR-12), and "Forbidden page: not listed in the sidebar" conflicts with Viewer read access to every configuration page (EXPERIENCE L132–133, L218, L229, L231, L245, L247, L251). *Fix:* add a role column or a capability-to-surface table, define the Editor treatment of Owner-only controls and copy, and rule on who creates the first secret when an Editor creates a confidential Application.
- **[high]** The Login branch isn't closed. L346 covers password enabled, and code replacing it when password is off. It doesn't cover an Application with only Passkey or social Connections, where Continue has no next step, nor an Application with zero Connections, although L221 warns the Admin about that case. "Use a recovery code" is only placed on the password step, so a Passkey-only User on a code-step Application has no entry. Disabled sign-up (FR-17) doesn't appear on Login, and arrival with a reusable Session (FR-14) isn't defined (EXPERIENCE L145, L221, L346). *Fix:* add a decision table of enabled Connections by identifier-step outcome, including recovery entry placement and each empty case.
- **[high]** Admin FR-46 recovery surfaces are absent. The Admin sign-in row has no path for an offline Recovery Code, though FR-46 says it sets up a new credential. There's no way for another Deployment Owner to recover a lost credential, no Admin self-service for credentials, no Admin sign-out, and no contents for the avatar menu for non-owners (EXPERIENCE L61, L205, L207, L257). *Fix:* add rows for each, or mark them explicitly as Operator tooling with the FR reference.
- **[medium]** The Tenants list has no state row or map row, although the avatar menu links to it and Delete Tenant returns to it. Create Tenant's entry point after the first Tenant is undefined. Landing is undefined for an Admin with no Tenant Roles, a Deployment Owner holding no Role, or after the last Tenant is deleted. The current Tenant being deleted or a Role removed mid-session also has no state (EXPERIENCE L44, L61, L209, L256). *Fix:* add a Tenants row and a no-Tenant-Role landing state.
- **[medium]** The Re-authentication gate conflicts with the modal rule. `button-destructive` always opens `modal`, Admin re-authentication is itself a "Modal", `modal` is one level deep, and "modals over modals" are banned. Yet Flow 9 says re-authentication fires first and then the modal states the impact, while `Session expired` can open over any modal and One-time reveal's "closing asks for confirmation" implies a second layer. Admin re-authentication also sits under a section said to be "all built from `hosted-card`" (EXPERIENCE L91, L102, L105, L107, L135, L200, L208, L310, L485). *Fix:* commit one sequence: for example, confirmation modal, then the browser sheet with no second modal, with failure shown inside the same modal. Define the reveal's close confirmation inline.
- **[medium]** Email-link landings are unresolved. Password changed's "Log in" and Email verified's "Sign in to continue" assume an Application to return to, but FR-47 binds the sign-in transaction to the initiating browser, so a link opened elsewhere has no transaction (EXPERIENCE L161, L175, L350). *Fix:* define the fallback: store the Application with the link and start a new request, or show a terminal "You can close this page" state.
- **[medium]** Account Portal rows leave out required states: change password, add or remove Factor, Regenerate Recovery Codes, email-change verification landing, 72-hour reversal landing, and portal entry with no Session. FR-47 binds sign-in to an Application, and the portal has none defined. The portal uses Skeleton while the Hosted global row says it's server-rendered and arrives complete (EXPERIENCE L125, L193–196). *Fix:* add a row for each action, name how portal sign-in gets its transaction context, and pick one loading model.
- **[medium]** Social sign-in has no Hosted state: provider cancelled, provider error, and unverified-email refusal (FR-20) have no screen, although FR-33 requires one for every error state. `Social email conflict` covers only one outcome (EXPERIENCE L186, L231). *Fix:* add a Social return row.
- **[medium]** Email recovery waiting has no entry point. Nothing says where a Passkey-only User starts it, how that start stays indistinguishable for unknown identifiers (NFR-20), or what screen the 24-hour link opens (EXPERIENCE L176, L435). *Fix:* name the trigger and landing, for example via Forgot password with an unchanged neutral confirmation.
- **[medium]** Passkey-only Users are missing from the MFA method picker. It lists security key, TOTP and Recovery Code, while Flow 3 sends every Always email-code sign-in to the MFA challenge. Such a User has a valid Passkey that the picker doesn't offer. Passkey creation's "Unsupported device: skipped silently" also has no outcome under Always, where enrolment is mandatory (EXPERIENCE L149, L162, L425). *Fix:* add Passkey to the challenge options, and route unsupported devices to Factor choice under Always.
- **[medium]** "Passkey or security key" in Factor choice is one row with two setups, and "Matching setup" doesn't say which. Passkey creation issues a first-factor credential and security key setup a Factor, which differ under FR-25 (EXPERIENCE L163–165). *Fix:* commit one path, or split the row. Splitting changes copy only.
- **[medium]** Settings required by FRs have no assigned screen: sign-up off (FR-17), Dev verification off (FR-17), terms URL (FR-17), Passkey prompt off (FR-21), code Connection creates accounts (FR-22), email recovery allowed (FR-27). A story author can't tell where to build them (EXPERIENCE L228–233, L245, L255). *Fix:* place each in the relevant state row.
- **[low]** There's no Admin not-found state for a deleted or unknown object URL, and no statement that an unknown Tenant Subdomain gets a generic rejection (FR-7) (EXPERIENCE L119–139). *Fix:* add two global rows.
- **[low]** Hosted "Offline: Same" assumes `banner` or inline handling, but JavaScript-off and server-rendered form posts show a browser error page. "Session and code expiry warn before they end" has no treatment (EXPERIENCE L138, L324). *Fix:* say the browser page is accepted for offline, and define or remove the expiry warning.
- **[low]** "Email code" attempts text needs a value for unknown identifiers, since NFR-20 requires identical behaviour. The row doesn't say the count is simulated (EXPERIENCE L148, L275). *Fix:* add that attempts count down identically when no code was sent.

### Findings

- **[critical]** "Use a recovery code" on the password step is shown for every identifier, and Recovery Code entry's success is "Signed in". FR-27 allows a Recovery Code to replace only the Factor step, and to replace the sign-in only for a Passkey-only User. Nothing says what happens when a User with a password and Factor uses this link, so as written an email plus one Recovery Code skips the password, breaking FR-25 under Always. design-consistency's own note says a code replaces only the Factor step for anyone with a Factor (EXPERIENCE L152, L346, L435; memlog L13). *Fix:* commit that first-factor Recovery Code entry succeeds only for Passkey-only accounts, and every other case shows the same "That code isn't valid." and doesn't consume the code. After Never to Always, Priya goes straight from password to Factor choice to TOTP setup, with nothing beyond the password. The flow's reasoning, "An unverified email can't enrol, so a stolen password alone can't add a Factor", doesn't follow: an attacker with the password of a verified account passes that check, enrols their own Factor and owns the account. Factor choice's row has the same gap (EXPERIENCE L163, L439–446). *Fix:* add email-control proof, such as an email code, before first-Factor enrolment at sign-in. Owner to confirm this reading; if the owner accepts a verified flag as enough, the FR needs correcting through `bmad-correct-course`.

The sentence is only true for the verified-Factor branch (EXPERIENCE L184). *Fix:* split the success cell: Factor path continues; reset link path ends at Password changed.
- **[high]** The Tenant page keeps deferred controls, although its row says "Drawn, changed". Export L1294 has the "Advanced · OIDC & OAuth" block: client-initiated backchannel logout (FR-24 v2), Device flow charset and code length (v2), plus "Default directory", and an external "Logo URL" that also breaks FR-34.
